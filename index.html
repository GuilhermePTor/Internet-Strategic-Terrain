Critical Minerals Platform: project plan

One project that starts as a quick dashboard and grows into a full data platform, one tool at a time. Every phase ends with a working dashboard.

0%

How this plan works

  • Build a thin version of the whole thing first (data, metrics, visuals), then upgrade one layer at a time.
  • The dashboard stays constant. Only what sits underneath it changes, so every upgrade is visible.
  • Each phase adds one tool and one visible improvement. Never break the previous version: tag it and keep going.
  • Every task is sized for about one hour. Each task has a short Why so you know what you are learning.
  • Tick tasks as you go. Progress is saved in this browser automatically.

Research question

How dependent are importing countries on a few suppliers for critical minerals (starting with Germany and natural graphite), and how much of that supply comes from countries that restrict exports?

Conventions for every phase

  • Dashboard tool: Streamlit + Plotly (free, easy to publish). Power BI works too for the same visuals.
  • The dashboard always reads one results table with fixed columns: year, commodity, reporter, partner, import_value_usd, share, hhi, restricted_flag, exposure. Do not rename these later.
  • Keep docs/decisions.md, add a screenshot to the README and create a git tag at the end of each phase.
  • Never commit secrets, raw data or Terraform state.
  • Check free-tier limits and quotas (Comtrade, GCP, BigQuery) when you start each phase, since they change.
  • If a task takes more than two sessions, split it or simplify it.

Key metrics

  • Supplier share = partner import value / total import value, per year and product.
  • HHI = sum of squared shares x 10,000. Higher means more concentrated. State which threshold you treat as highly concentrated (commonly above 2,500).
  • Restriction exposure = share of imports coming from partners with an active export restriction on that product.

Overview: progress at a glance

Cross-cutting habits

  • Tag a release at every milestone (v0 to v1.0-capstone) and keep a CHANGELOG.md.
  • Keep one screenshot per tag. Side by side they make a visual timeline for your README or LinkedIn.
  • Write one paragraph per phase in docs/decisions.md: what you chose, why, and what went wrong.
  • Update the architecture diagram at the end of every phase.
  • Check that the Phase 0 baseline numbers have not changed unexpectedly. If they have, you found a data issue or introduced a bug: write it down.
  • Phases 1, 2, 5 and 6 add few new charts by design. A phase that adds trust or reliability is still progress, which is why each one adds a dedicated page.
